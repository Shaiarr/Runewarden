# Runewarden 0.9.5

This plugin update adds an integrated World hopper, protects Varlamore rendering from unavailable NPC definitions, reduces duplicate route work, improves account-aware travel planning and corrects action identity and completed-batch display.

## World hopper

- The compact world table shows current/previous-world context, native country flags and US East/West coast details. It supports world-number or activity search; All/Free/Members selection; multiple region and native type selections; recommended eligible worlds; favourites-only and pinned favourites.
- World, Players, Ping, Type, Location and Activity sorts support both directions. Unknown ping/unavailable population values remain after known values. Region and type multi-selection use OR within each group. Type grouping distinguishes High risk from PvP and includes Tournament within Seasonal. Current-world context remains visible when filters exclude its row.
- A selected row has an explicit Hop action. Optional double-click, Enter and row-menu hopping share the backend checks; row menus also manage favourites. Return world is separate from Previous/Next cycling. Configurable quick-hop keys start unbound and use the saved filters and compatible native world mode. The local command is `::rwhop <world>`. Online friends, Friends Chat, clan and guest-clan members have an optional Hop-to (Runewarden) menu entry.
- Logged-in requests check current/offline/full worlds, membership and applicable members/F2P total-level requirements. Special-world types, including Legacy/EOC flags, remain manually selectable through explicit Confirm hop/Cancel controls; RuneLite's native entry restrictions and confirmations still apply. A queued target whose type changes requires a fresh manual warning rather than reusing the earlier approval. Every execution rechecks the current profile, world descriptor and eligibility. Opening the native switcher is limited to three attempts, and its blocked-action message cancels the request.
- Hops originate only from explicit player actions. Background ticks finish that single request through RuneLite's public world-switcher APIs; they do not choose emergency hops or bypass native confirmations. Login-screen selection uses the native world-selection API.
- Favourites and panel choices are character-bound. The two native favourite slots are read without rewriting them; a character can locally hide one. Refresh worlds and Refresh pings are separate controls. Activity/location display, favourite pinning and double-click behavior are saved. Updates preserve selection and scroll; there is no Swing polling timer. Country icons come from cached native RuneLite resources, without copied assets or network image requests.
- The official world list is loaded off the client thread, refreshed no more than once per minute while visible, and updated from native list/population events. One bounded worker performs official-host TCP connection probes with a one-second connect timeout. OS DNS resolution can still block that single worker; cancellation does not start replacement workers. Stopping retires idle worker threads immediately, and a restart reuses the same bounded executor and in-flight guard. Background probes are spaced by at least three seconds, with current-world priority after six seconds when requested; these are scheduling intervals, not response-time guarantees. Hidden/disabled views stop work unless the current-world HUD requests measurements. Profile, lifecycle and connection-generation checks discard stale results, including leaving and returning to the same world.
- The optional movable current-world HUD paints published measurements without network work. TCP latency and supported native TCP_INFO retransmission samples remain unknown when unavailable; the retransmission estimate uses sixteen samples. Logout clears the HUD's current connection state. This is a current measurement display, not a network-history or lag-analysis engine.

The comparison uses RuneLite's pinned 1.13.2 World Hopper source. Deliberate differences include the `::rwhop` namespace, unbound default keys, applying all saved filters to quick-hop, an additional explicit special-world warning, character-owned favourites and TCP-connect probes instead of native ICMP-first measurements. Native current-ping sampling is more frequent. This establishes the listed source-level mechanisms rather than identical timing or complete undocumented-option parity. Native behavior attribution and the full BSD notice are retained in [third-party notices](third-party-notices/world-hopper-runelite.txt) and the plugin resources.

## Plugin scope and diagnostic limits

- Reported development-client failures included Java heap exhaustion under a 768 MiB maximum heap. Installed system RAM does not change that JVM limit. This evidence does not identify a leaking plugin or establish which component retained the memory.
- This release changes the plugin and its tests/resources. Existing launcher, JVM heap settings, client runtime and vendored plugins are unchanged. The production plugin JAR and source are the review artifacts; the existing development client remains a test harness.
- Runewarden's Varlamore scene overlay rejects despawned/replaced NPC snapshots, missing native compositions and mismatched world views before projection. Missing local-player and logout/hop states are covered by its own regressions. This scope is the plugin's Varlamore overlay.
- Duplicate route requests are coalesced inside Runewarden rather than changing the client heap or removing navigation/HUD functions. The observed global heap failures remain unproven fixed; all-client and third-party overlay exceptions are outside this fix's demonstrated scope.

## Navigation

- Automatic farm-guide preparation supplies eligible matching native patch destinations to Shortest Path as a target collection. Its actual graph and transport costs choose the arrival from the current position, carried/equipped items, runes/charges, native unlocks and known house travel options. Runewarden does not duplicate those decisions with a town-distance heuristic.
- Teleport item requests use the native Inventory mode, covering currently carried and equipped items rather than banked-only possessions. Rune-pouch quantities, transport-related items and native account facts remain inputs to the actual upstream solver.
- An active custom farm run keeps its real next stop and configured order. Observed native anchors and saved player pins take priority over sourced farm-area markers. Unsupported or still-loading destination information does not create a fixed Taverley fallback.
- Requests capture and validate the current native origin. Explicit Travel planning displays an owned path with its per-route transport options and refreshed native account/item/house inputs. Runewarden sends no Shortest Path query messages and starts no second search for its summary.
- The result reader uses fixed public method names through `getMethod` and public getters on the active optional plugin. It requires a completed search, a non-null published result and exact owned target-set/origin/profile/generation matches. It copies at most 64 target points and twelve instruction strings, retaining no native path/search/graph. Unsupported public APIs or incomplete results leave the summary unknown. Transport events only wake the reader; they do not prove completion, and tick polling also handles completion without an event.
- One summary read can remain pending. Capability changes coalesce to at most one automatic replan per three ticks; a position jump over sixteen tiles can replan immediately. Old cape/portal advice clears while replanning. Stable ticks do not repeatedly request the same path. A player's replacement path releases ownership; clearing still checks the exact owned target collection.
- Farm route advice comes only from a completed owned Shortest Path result matching the current profile and destination. It displays the selected transport chain, or walking near a patch. Failed, foreign or unavailable results do not generate a substitute teleport recommendation. House/instance position changes can refresh solver advice without scanning outside farming patches.

## My POH and observation boundaries

- Travel's My POH panel saves a character's portal/nexus selections, fairy ring, spirit tree, obelisk, jewellery-box tier and four supported mounted items: glory, Xeric's talisman, digsite pendant and mythical cape. A fresh unknown house has no assumed jewellery box or mounted items. Existing user-managed native Shortest Path declarations remain authoritative; they are not a new native observation.
- The retained source catalogue contains 40 portal destinations, 127 distinct direct portal object IDs and 903 native transport requirement/alias item IDs. These identify supported source facts and relevant route revisions, not an assertion that the player owns every destination. Ordinary herb quantity changes do not cause a travel replan.
- Automatic portal observations require an instanced native POH template and building-mode ownership proof. The scan reads current-plane direct portal objects and live Nexus widgets. Cached nexus menu entries may come from another house, so they remain suggestions until the player confirms them. Normal-mode house ownership is not inferred.
- Only the explicit Use my POH for routing action applies the selected supported native house settings. The action checks its character/profile generation; ordinary route calls supply supported ephemeral options instead of rewriting house declarations. Owning a Construction cape or reaching 99 Construction never implies portals, mounted items or an ornate jewellery box.
- Native house declarations are global upstream. A guarded applied-settings fingerprint prevents another character from borrowing the unchanged house set applied by Runewarden. Character selections remain saved; after another character applies a different house, the previous character must explicitly apply its selection again. Independently modified native declarations are respected.
- Outside instances, requests use the current native position. Routing from inside a house requires the verified own-POH source template and building-mode proof, then uses Shortest Path's documented virtual house origin. Guest houses, normal mode without ownership proof and other instances remain blocked. The actual Construction cape → known house → Catherby chain is tested; these bounds do not establish universal POH routing or unlock discovery. The plugin presents routes without performing teleport or movement actions.

## Action progress

- Native item operations or matching inventory and XP transformations capture the title, icon and skill together. A selected training or Banked XP recipe cannot label unrelated work. An ambiguous gem animation alone does not establish a specific item.
- Unrecognized non-production animations do not produce a generic Current action HUD. Confirmed zero-remaining batches and their matching cycles disappear; fresh materials reset the batch count.
- Producer regressions cover cleaning toadflax despite an emerald animation alias, observed XP/item work overriding a selected method, rejection of alias-only identity and completion/fresh-batch transitions.

## Verification and release limits

The clean JDK 17 build passed 1,620 Java tests across 195 suites, with no failures or skips. All 32 Python checks and 96 dataset fingerprints passed. The Java 11 production JAR contains 771 classes and 153 matching resources. The audit verifies 259 source/test evidence files. All 1,472 frozen build/source inputs remained unchanged during verification; their hashes and actual results are recorded in `automated-inputs-0.9.5.json` and `automated-evidence-0.9.5.json`.

The full suite passes with the unchanged 768 MiB test heap. A diagnostic heap dump identified synthetic Mockito fixture retention through thread-local mock state on idle hopper workers. Immediate idle-thread retirement breaks that reference chain; a real-worker regression verifies termination and successful restart on the same bounded executor. This test-only diagnosis does not establish the retained-memory owner or resolution of the reported live-client heap failure.

Navigation regressions cover eligible multi-target farm preparation, custom-order preservation, current-origin requests, solver-derived transport advice, partial/stale/foreign result rejection, bounded/coalesced refresh, completion without an event and zero query messages. The native Shortest Path integration checks the actual Construction cape → house → known Catherby portal edge chain and a changed origin after teleport. It also checks nearby walking and a carried Camelot tablet winning over a known house/cape when cheaper. These are headless source-level integration cases, not logged-in gameplay results. Varlamore regressions cover missing compositions, replaced/despawned snapshots and player/profile lifecycle states. World Hopper regressions cover entry eligibility and native confirmations, changed pending-world types, manual actions and quick-hop filters, character ownership, bounded off-thread work and stale connection results. Native-width Swing cases exercise table/filter/sort behavior, risk controls and profile restoration; they do not establish logged-in world switching or live network measurements.

The production JAR uses standard RuneLite public APIs and excludes the development launcher, client/runtime and companion plugin classes. Shortest Path remains an optional external plugin reached through its public message contract. Retained upstream code is used for development integration tests. Guide opening, progress, completion and dismissal from 0.9.4 remain in scope.

Windows execution and logged-in behavior require actual live acceptance. All ten live/review gates remain open until evidence records a pass. Plugin Hub review remains pending. The capability audit retains the 151-plugin snapshot and its explicit partial and missing specialist features.
